# 布局类问题排查方法论

> 创建：2026-09-02 · 源自 `docs/bugs/007-ios-standalone-pwa-bottom-gap.md` 的排查复盘

本文沉淀一次「iOS Standalone PWA 底部 62px 留白」从「被判无解」到「定位到语义冲突」的完整排查思路，可复用于任何「看似无解 / 归因黑盒」的布局问题。

---

## 核心心法

1. **先证明「试过了」，再谈「做不到」。** 任何「无法触及」「系统原生层」的结论，都必须先证明"我确实穷尽了所有能触及的手段"。
2. **病根多在「语义冲突」，不在「浏览器有 bug」。** 浏览器谎报只是把冲突暴露出来，修语义不修表象。
3. **区分「真债务」和「伪债务」。** 看起来该清理的东西，先搞清它为什么存在——"有意的层级"不是"重复的冗余"。

---

## 排查路径（以本次为例）

### 第一步：怀疑「无解」结论

原文档断言 62px 空白是「系统原生层，任何 DOM 与 CSS 均无法触及」。可疑点在于：它把问题归因于一个**无法验证的黑盒**，而论证链条里有两处测量缺陷。

**触发点**：凡结论依赖"测出来是 0 / 是空"的，先怀疑测量方法。

### 第二步：找到测量方法的错误

**错误 1 —— `env()` 读法错**：

```js
// ❌ 参数是属性值，getPropertyValue 只会返回空串
getComputedStyle(el).getPropertyValue('env(safe-area-inset-top)')  // → ""

// ✅ 把 env() 用在真实属性上，再读计算值
el.style.paddingTop = 'env(safe-area-inset-top, 0px)'
getComputedStyle(el).getPropertyValue('paddingTop')  // → "62px"
```

原文档把「空串」误读成「0」，推导出「安全区没被感知」——实际上一直是 62px，从未为 0。

**错误 2 —— 只测了"恰好会说谎"的值**：

只测 `dvh` 和 `innerHeight`，这两个恰是 iOS standalone 冷启动下唯二少报 62px 的值；
漏测 `100vh` / `100lvh`——它们才是判断「62px 可达不可达」的决定性证据。

**教训**：漏测不奇怪，奇怪的是据漏测结果下绝对结论。测「会不会说谎」时，要同时测「会说谎的」和「不会说谎的」两类值做对照。

### 第三步：真机实验（决定性证据）

用探针页在真机测出关键对照表 + 一个「涂紫」实验：

| 值 | 实测 | 判定 |
| --- | --- | --- |
| `100vh` / `100lvh` | 874 | ✅ 可信 |
| `100dvh` / `100svh` / `innerHeight` | 812 | ❌ 少 62 |
| `env(top)` / `env(bottom)` | 62 / 34 | ✅ 真值 |

「涂紫」把 `100vh` 层染品红，看它能画到哪——**紫色铺满物理屏最下沿**，一举推翻「系统层不可达」。

**交叉验证**：62px 不是底部 home indicator，而是**顶部** inset。iPhone 14 Pro（852pt）差 59、iPhone 16 Pro（874pt）差 62，差值恒等于各自的 `env(safe-area-inset-top)`。

### 第四步：第一性原理找根因

不满足于"WebKit 报错数了，绕开它"（那是补丁）。要问：**为什么这 bug 只在我们身上出现？**

答案是**语义冲突**：

- 项目选了 `viewport-fit=cover` **全屏延伸模型**——绘制区 = 整块物理屏，系统 UI 叠加其上、用 `env()` 单独避让；
- 但高度来源用 `height: 100%` **百分比链**——解析到 ICB，而 ICB 语义是「可见区」，standalone 下被 WebKit 报成 812。

**选了 A 模型，却用 B 模型的尺寸来源**，两者天生矛盾。

### 第五步：让单位回归正确语义，而非绕开表象

全屏延伸模型下，高度语义就是**大视口** `100lvh`，而不是「跟随可见区」的 `dvh`/`svh`。

```
--viewport-height: 100vh;              /* 基线，全平台无条件支持 */
@supports (height: 100lvh) {
  :root { --viewport-height: 100lvh; } /* 增强：显式大视口语义 */
}
```

这是「让单位回到已选模型的正确语义」，不是「换单位绕过 bug」。

## 过程中常见的自我纠正

### 别只看眼前，查依赖关系

一度建议「去掉 `.orbit-shell` 的 `position: fixed`」。但查 `Layout.tsx` 发现
`.orbit-sidebar-panel` / `.orbit-overlay-scrim` 都是 `fixed inset-0`，**以 shell 为包含块**。
去掉 fixed，它们退回 viewport(812)，比 shell 矮 62px，反而制造**新**空白。

**教训**：改一个属性前，先查"谁依赖它的当前值"。`position` 会改变后代 `fixed` 的包含块。

### 「该清理」≠「真该清理」

compose 编辑器 11 个 `.dark` 选择器写了 6 档背景亮度 + 4 档边框，看似「重复写死」。
细查发现是**有意的层级深浅**（footer 最暗、segment 激活最亮），本质是暗色 surface
层级 token 缺失。机械替换成 `--color-surface` 会压平层级、引入视觉回归。

**教训**：区分「冗余」与「缺失」——值是各写各的，不一定是在重复同一值；先搞清"为什么存在"，再决定动不动。

## 可复用的检查清单

面对「看似无解的布局问题」：

- [ ] 结论是否归因于黑盒？→ 先证明"试过了"，穷尽所有能触及的手段
- [ ] 测量方法是否正确？（`env()` 读法、单位覆盖是否完整、是否测了对照组）
- [ ] 是否做了决定性实验？（不是推断，是能一锤定音的可视化验证）
- [ ] 是否追问"为什么只有我们"？（而非停在"它 bug 了"）
- [ ] 根因是「语义冲突」还是「浏览器 bug」？（前者修语义，后者才谈 workaround）
- [ ] 改动前是否查了依赖关系？（谁依赖当前值，改了会不会连锁）
- [ ] 该清理的是「冗余」还是「缺失的层级」？（别压平有意的层次）
